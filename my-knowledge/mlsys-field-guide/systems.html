Systems rule

Name what moves, over which link, how often, and who waits. Then attach a trace—not just a peak-hardware number.

Latency is a path. Throughput is a workload.

Parallelism changes which bytes move during training. Serving changes when requests wait. Online RL couples an inference fleet to a learner. Profile each boundary with an explicit workload, version, and trust model.

Carry the mesh into the inference lab

Prefill and decode stress different ceilings.

Prefill processes the prompt in parallel and can reach high arithmetic intensity. Decode advances one position per active sequence, repeatedly reading weights and an expanding KV cache; at small batches it is commonly bandwidth-bound.

Read the result correctly

The weight-stream term assumes one pass over quantized weights per batch step and perfect reuse across the batch. The KV term assumes the full average cache is read. Real kernels tile, fuse, shard, and overlap work; TP/PP add communication. Measure the exact engine on a prompt/output-length distribution and report p50/p95/p99.

A larger batch can raise throughput while worsening latency.

The numerator gains more active sequences per weight stream, but queueing and per-step KV traffic grow. Capacity planning is an SLO optimization, not “maximize tokens/s.”

Policy-freshness inspector

Version laglag(τ) = vlearner, consume − vactor, generate

On-policy ideal

Generate with the current policy and update promptly. This reduces distribution mismatch but creates synchronization barriers and idle hardware.

Asynchronous reality

Actors and learner overlap, so trajectories can be stale. Bound lag, record both policies’ log-probabilities, monitor importance ratios, and define when stale samples are dropped.

Backpressure

A bounded queue should slow prompt admission when learner consumption or verifier capacity falls behind. Watch queue age, actor utilization, effective batch, zero-advantage rate, lag percentiles, and weight-sync time.

OlmoRL: separate primary-source accounts

source configurations differ

Olmo 3 technical report, arXiv v2. The report describes an off-policy asynchronous actor–learner setup with continuous batching and inflight actor-weight updates. For same-prompt groups, its advantage removes the group mean without dividing by the reward standard deviation; training also corrects mismatch between vLLM behavior log-probabilities and the learner. The source-specific measurements below are intentionally not merged.

Static-batch idle fractionwaste = (Lmax − mean(L)) / Lmax = 1 − mean(L) / Lmax

arXiv v2 length example. The report gives 14,628 mean versus 32,000 maximum generation length; the static formula gives about 54.3% waste. This is a workload-specific upper-bound comparison, not a universal serving constant.

arXiv v2 · production resource split32B: 8 H100 nodes for the learner and 20 for inference; the learner waited about 75% for data, with roughly 5× inference compute. 7B: 2 learner nodes and 7 inference nodes, with roughly 14× inference compute.
arXiv v2 · Table 23 ablationTwo 8×A100 nodes for 2 hours, one training and one inference; 64 prompts × 2 samples = 128 completions per step; maximum output 32,000 and input 2,048. Table 23 reports 881 → 975 → 1,358 → 2,949 tokens/s across the four cumulative configurations.
arXiv v2 · stated headlineThe report says inflight updates avoid actor pauses and KV-cache invalidation and can reach up to 4× throughput at the same resources. Keep that prose claim scoped to the report; it is not a universal speedup or a recomputation of Table 23’s endpoint ratio.
Author blog · H100 benchmarkQwen 2.5 7B; 16 prompts × 4 samples; maximum 32k output and 2k prompt; two 8×H100 nodes, one trainer and one actor node; 8 one-GPU actors; 2 hours. The blog lists the same 881 → 975 → 1,358 → 2,949 tokens/s sequence and links implementation commits.
Reconciliation statusThe arXiv-v2 and author-blog configurations differ in accelerator and prompt/sample counts even though the throughput sequence matches. Treat them as two attributed source claims until the discrepancy is reconciled; no blended row is an “exact” benchmark.
Systems interpretationQueueing and synchronization changes can dominate utilization, but every measurement must retain its model, batch construction, hardware, actor layout, duration, code revision, and source.

Code ownership boundary

external stack

This OLMo-core checkout has no PPO, DPO, GRPO, reward/verifier, actor fleet, rollout queue, or RL weight-synchronization orchestration. Its trainer/FSDP components can be reused by another project; reuse does not move orchestration into this repository.

Open Instruct’s GRPO documentation is the adjacent implementation boundary: it uses Ray and vLLM and describes implementations built on OLMo-core’s native training infrastructure.

  • Olmo 3 technical report · arXiv v2 — asynchronous algorithm, production resource ratios, and the A100 64×2 Table 23 ablation.
  • Making RL Fast — author blog’s distinct H100 16×4 benchmark description and commit-linked table.
  • TransformerTrainModule — reusable learner-side training substrate in this checkout.
Online versus offline is a data-generation distinction.

PPO/GRPO-style online methods repeatedly sample from a behavior policy and must manage policy lag. DPO trains from an existing preference dataset and has no online actor loop in the optimization step, though the preference data still has a generation provenance.
